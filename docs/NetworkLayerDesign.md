## 0. 先解决一个冲突：Asio 还是自研 Poller

`IBFAICONTEXT/week3.md` 里写的计划是「用 Asio + C++20 协程实现 TCP 和 UDP 通信」。本文档是**自研 Poller + 分片事件循环**路线，两者只能选一个，不能混。

| | 自研 Poller（本文档） | Asio + 协程 |
| --- | --- | --- |
| 平台差异 | 自己封，能看见 epoll/kqueue/WSAPoll 的真实行为 | 库替你封，看不见 |
| 与现有 ThreadPool / TaskQueueLoop 的配合 | 直接配合，线程归属自己说了算 | 要么全进 Asio 的 io_context，要么两层事件循环打架 |
| 学习收益 | 高（这正是本轮的目标） | 低 |
| 达到 75% 的难度 | 中，取决于下面每一步做不做对 | 低，Asio 自己就是工业级 |
| 风险 | 自己会踩连接生命周期、丢唤醒、fd 复用这些坑 | 坑少，但控制感弱 |

**决定：走自研路线**，理由是本次目标本身包含「要能自己动手做出来」和「要理解平台差异」。如果以后发现吞吐长期上不去、且瓶颈确认在 IO 模型本身，再评估要不要换。

## 1. 先定分母：性能指标怎么定义

「效率达到工业级 75% 以上」这句话在定义清楚之前无法验证。开工前必须钉死四个数，写进配置或基准脚本里：

| 项 | 说明 | 建议取值 |
| --- | --- | --- |
| 对比对象 | 75% 是相对谁的 75% | 一个成熟框架在相同硬件、相同协议、相同负载下的吞吐 |
| 消息大小 | 请求/响应各多少字节 | 小包 200B、中包 4KB、大包 1MB 三档分别测 |
| 单请求业务耗时 | 处理器里实际干活的时间 | 0µs（纯 echo）、100µs、1ms 三档 |
| 并发连接数 | 同时保持的连接数 | 100 / 1000 / 8000 三档 |

三类指标分别看，不要混成一句话：

1. **吞吐**：每秒完成的请求数（QPS）。这是「75%」通常指的东西。
2. **单核效率**：QPS ÷ 使用的 CPU 核数。这决定了加机器能不能线性扩容。
3. **尾延迟**：p50 / p99 / p99.9。工业级和玩具的分界线几乎总在这条线上。

**一个必须接受的结论**：业务耗时越长，框架开销占比越小，越容易达到 75%。如果对比的是「纯 echo」这种零业务负载，框架里每一次多余的分配、每一次多余的唤醒都会直接体现在成绩单上。所以第 1 步不是优化，是**先建一个能重复跑的基准**（里程碑 M10 的脚手架在 M0 就要搭好，否则后面所有优化都是猜）。

## 2. 总体架构与并发铁律

### 2.1 分层

```
                      ┌──────────────── 业务线程池（10 条，TaskQueueLoop 或后续的轻量池）
                      │  只做：查表 → 解析 → 业务 → 组装响应字节
                      │  绝不碰 socket、绝不碰连接对象
                      │
 客户端 ──TCP──► Listener（1 条线程，只 accept）
                      │  accept 后把新连接交给某个分片
                      ▼
              ┌───────────────┬───────────────┬───────────────┐
              │  分片 0        │  分片 1        │  分片 N        │  每分片 1 条线程
              │  EventLoop     │  EventLoop     │  EventLoop     │  各持一个 Poller
              │  ~1000 连接    │  ~1000 连接    │  ~1000 连接    │  连接独占，无需锁
              │  读缓冲/写缓冲 │  ...           │  ...           │
              │  定时器        │                │                │
              └───────────────┴───────────────┴───────────────┘
                      ▲                                    ▲
                      └──── 唤醒器（eventfd / 回环 socket）────┘
```

分片线程只做三件事：等 IO 事件、收发包、把完整的帧丢进业务池。业务线程池只做纯计算。两边只通过两条队列通信。

### 2.2 一次请求的完整生命周期（标出跨线程边界）

1. 内核收到字节 → 分片 Poller 返回「连接 X 可读」。
2. 分片对 X 调 `recv`，字节追加到 X 自己的读缓冲。
3. 分片在读缓冲上拆帧；拆出完整帧后，把自己对 X 的读关注摘掉（一条在飞）。
4. 分片把「连接标识 + 完整帧」投进业务池队列，**唤醒一个**业务线程。 ← 跨线程边界 1
5. 业务线程查指令表、解析、跑业务、组装响应字节。
6. 业务线程把「连接标识 + 响应字节」投进该分片的待发送队列，**唤醒该分片**。 ← 跨线程边界 2
7. 分片把字节倒进 X 的写缓冲，关注可写。
8. 分片在可写事件里 `send`；发完（写缓冲清空）后恢复 X 的读关注（一条在飞结束）。

整条链路上，跨线程传递的信息只有「一个能识别连接的标识」和「一段字节」。这是这套架构最省心的地方，请守住。

### 2.3 并发铁律（违反任何一条都会出「偶发、难复现」的问题）

1. 一条连接在任一时刻只属于一个分片；只有该分片线程能读写连接对象和它的 socket。
2. 跨线程只传「连接标识 + 字节」，不传裸 fd、不传连接指针的强引用。
3. 连接对象的销毁只能发生在分片线程上，且必须同时满足：在飞请求已归零、写缓冲已清空、已从 Poller 里删除。
4. Poller 里每个 fd 注册的「用户数据」是连接标识（指针或索引 + 代次），不是裸 fd。内核会复用 fd 号，靠 fd 号认连接迟早认错。
5. 从 Poller 删除 fd 必须在 `close` 之前，且都在分片线程上按顺序做。
6. 业务线程绝不调用 `recv` / `send` / `close`。
7. 跨线程共享的状态（通常是每分片的待发送队列）由一把明确的锁保护，锁内不做 IO、不做内存分配之外的耗时动作。
8. 「一条在飞」的摘除与恢复必须成对，由同一个状态机裁决，不能在两个地方各写一半。

## M0 目录、接口占位与基准脚手架

**为什么**

网络层的绝大多数争论（要不要改缓冲、要不要换唤醒方式、epoll_ctl 值不值得省）都是「几个微秒」级别的争论。没有基准，这些决定只能靠感觉，最后会变成反复推翻自己。所以第一件事不是写 IO，而是先能测量。

**思想与做法**

- 先定目录和文件边界，接口带注释但不实现（能编译，能跑，跑起来什么都不做）。
- 同时写一个最简客户端工具：能建 N 条连接、按指定大小和频率打请求、统计 QPS 和延迟分位数。它就是以后所有测试的标尺，也是网络层第一个真实使用者（客户端侧代码复用同一套协议编解码）。
- **分段计时**：一次请求的耗时拆成 6 段分别计数——`epoll 返回到 recv 完成`、`拆帧`、`入队`、`业务处理`、`回投到分片`、`send 完成`。用原子计数累加，按秒上报。这是后面定位瓶颈的唯一有效手段。

**交付物**

- 目录：`include/net/`、`src/net/`，按 M1~M9 的类名先放空壳。
- `NetServer`：对外唯一入口，负责启动监听、创建分片、启停。
- `NetStats`：分段计时的计数容器，接入 `ShineBasicModule` 的阶段自检。
- `tools/netbench`：压测客户端。注:tools用于放一些项目中需要用的小工具类，压测客户端放在test文件夹中

**指标**

- 空壳程序能启动、能收到 `status` 命令并打印 0 连接 0 收发的统计。
- 分段计时本身的开销 < 总耗时的 1%（用原子加法 + 每秒一次汇总，不要每条日志）。
- 压测客户端能在本机建立 1000 条连接并保持 60 秒不断开。

**验收**

`netbench` 指向一个「只接受连接、不回包」的空服务器，能稳定打印「已连接 N 条，保持 T 秒」。此时还没有网络功能，但标尺已经立起来了。

## M1 Poller 抽象与平台实现

**为什么**

平台差异如果散在业务代码里，以后加平台就是重写。所有「fd 怎么等」「事件怎么表示」的差异必须封死在一层里，上层只认统一事件。

**思想与做法**

- 抽象的核心不是「接口长得好看」，而是**三件必须统一的东西**：
  1. **句柄类型**：Linux 是 `int`，Windows 是 `SOCKET`（不是 int，且 `INVALID_SOCKET` 不是 -1）。定义一个不透明类型 `NetHandle`，上层不假设它是什么。
  2. **事件语义**：至少要能表达「可读」「可写」「出错」「对端关闭」四种。三平台的原始事件名和含义都不一样，必须映射成统一的四种，并且保证「对端关闭」在三个平台都表现为同一个事件（Windows 的 WSAPoll 在这一点上是有名的坑，要用「可读 + recv 返回 0」兜底判定）。
  3. **注册时的用户数据**：注册 fd 时附带一段用户数据（连接标识），事件返回时带回来。这是避免「用 fd 号认连接」的唯一办法。
- 平台实现：Linux 用 `epoll`（LT 模式，主力）；macOS 先用 `poll` 兜底并把 `kqueue` 留作扩展（`poll` 在 1000 fd 下每轮是一次系统调用，代价可接受）；Windows 用 `WSAPoll`，只做「顺带支持」，不作为主战场。
- 平台实现里统一处理这些杂事：`EINTR` 重试、`EAGAIN`、`EINPROGRESS`（非阻塞 connect 未完成）、SIGPIPE 的屏蔽（Linux `MSG_NOSIGNAL` / macOS `SO_NOSIGPIPE`）、fd 上限检查（Linux 默认 `ulimit -n` 是 1024，要主动查并记录）。
- 「等多久」这件事必须进接口：`Wait(超时时间)`，因为定时器（M8）没有它就没法实现。

**交付物**

- `Poller` 接口：注册/修改/删除/等待，句柄与事件的不透明类型。
- 三个平台实现文件，编译期按平台选一个。
- `SocketOps`：socket 选项与错误码的平台封装（非阻塞设置、`TCP_NODELAY`、`SO_REUSEADDR`、错误码翻译）。

**指标**

- 一次 `Wait` 只产生一次等待系统调用；1000 个空闲 fd 下分片线程 CPU 占用 ≈ 0%。
- 批量事件返回时，单个事件的处理成本 < 1µs（不含业务）。
- `TCP_NODELAY` 必须默认打开（请求-响应协议不开会把延迟拖到几十毫秒级）。

**验收**

写一个只测 Poller 的小程序：建立 100 对 socket、注册、互发、删除、重复 10 万次，无泄漏（退出前 fd 数归零）。三个平台至少 Linux 必须过。

## M2 唤醒器 Wakeup

> 这一节是本次评审里单独设计的内容，写完 M1 后紧接着做。完整设计见[第 4 节](#4-跨线程唤醒专项设计)。

**为什么**

业务线程算完结果要通知分片，但分片此刻正阻塞在内核的 `epoll_wait` 里。条件变量叫不醒一个阻塞在 `epoll_wait` 的线程，这是本架构最容易踩的第一个硬坑。

**思想与做法**：见第 4 节（一句话版：给每个分片配一个「能进 Poller 集合的通知对象」，写一次就唤醒，读一次就排空）。

**交付物**：`Wakeup` 接口 + 平台实现，每个分片持有一个实例并注册进自己的 Poller。

**指标**

- 唤醒成功率 100%（连续 100 万次唤醒零丢失）。
- 唤醒延迟：p50 ≤ 20µs，p99 ≤ 100µs（Linux 目标值）。
- 空闲分片不因唤醒器产生任何 CPU 占用。
- 通知可合并：同一分片在唤醒排队期间的 N 次通知只产生 1 次唤醒写。

**验收**：把它接进 M4 的分片循环，用「外部线程投一条空任务」的方式跑 100 万次，统计延迟分布和丢失次数。

## M3 连接对象与生命周期

**为什么**

这套架构里唯一真正危险的地方就是连接的生命周期：业务线程手上还捏着连接标识，对端突然断开，分片要销毁连接。这是 use-after-free 和数据错乱的经典来源，必须在写 IO 之前把规则定死。

**思想与做法**

- 连接对象**由分片独占持有**（例如分片内部用 `unordered_map<连接标识, unique_ptr<Connection>>`）。业务线程从不持有连接指针。
- 跨线程传递的「连接标识」要能识别「这条连接已经死了」。两种可行做法：**代次号**（分片维度自增，复用时要能对不上）或**弱引用/句柄表**。推荐前者，简单且无锁。
- 连接的销毁条件写成显式规则（三条同时满足）：在飞请求归零、写缓冲为空、已从 Poller 删除。销毁动作只在分片线程执行，且集中在「一轮事件处理结束后」的清理阶段，不要在事件处理中间顺手删。
- 连接状态机（**「一条在飞」的正式定义**，M6/M7 都依赖它）：

  | 状态 | Poller 关注 | 在飞 | 允许发生的动作 | 迁出条件 |
  | --- | --- | --- | --- | --- |
  | 空闲 Idle | 读 | 0 | 收字节、拆帧 | 拆出一整帧 → 在飞中 |
  | 在飞 InFlight | 无 | 1 | 等业务线程回投 | 收到响应字节 → 发送中 |
  | 发送中 Writing | 写 | 1 | `send` 写缓冲 | 写缓冲清空 → 空闲 |
  | 关闭中 Closing | 无 | ≥0 | 排空写缓冲或直接断 | 在飞归零且写缓冲空 → 销毁 |

- 读缓冲每连接一份，写缓冲每连接一份，都由分片线程独占访问（不需要锁）。

**交付物**：`Connection` 类、连接标识类型、分片侧的连接表、状态机实现。

**指标**

- 打开 8000 条连接时，进程内存增量可预测：`连接数 ×（两个缓冲的上限）` 量级，不出现随请求数增长的内存。
- 在飞未归零时绝不销毁连接（用日志或断言把违反次数钉在 0）。

**验收**：写「客户端发一半就断开」「客户端发完立刻断开」「客户端断开后服务器才开始回包」三类用例，配合 AddressSanitizer / ThreadSanitizer 跑，必须干净。

## M4 分片事件循环 Shard

**为什么**

分片是这套架构的性能单元：一个线程、一个 Poller、一批连接。它的实现质量决定了并发度和尾延迟。

**思想与做法**

- **不要复用现有的 `ThreadPool` 当分片线程**。原因很具体：`ThreadPool` 的线程数是编译期常量（10 条），实例化一个就起 10 条；这 10 条会并发执行同一个执行体，等于 10 条线程抢同一个 `epoll` 集合和同一批连接，「连接归分片独占」的前提当场失效。而且它的抽象是「共享谓词 + 共享执行体」，没有「每条线程各自一套循环状态」这个概念，而分片要的恰恰是每线程独立的 Poller、定时器、缓冲。
- 正确做法：单独写一个 `Shard`，只做四件事——`epoll_wait` ↔ 连接 IO ↔ 待发送队列 ↔ 定时器。两三百行，隔离性好，回归风险为零。如果以后想让 `ThreadPool` 也支持分片，前提是给它加「线程数参数」和「每线程上下文」，那是另一件事。
- 分片循环的一轮固定按这个顺序做：① 先排空待发送队列（把已就绪的响应倒进各连接的写缓冲）② 算下一次 `epoll_wait` 的超时（= 最近定时器到期）③ `epoll_wait` ④ 逐个处理事件（最多批量上限）⑤ 处理到期的定时器 ⑥ 清理待销毁的连接。
- 第 ① 步放在 `epoll_wait` 之前，是为了避免「业务线程刚投了结果、分片又睡进去」的额外一轮延迟；每次唤醒后第一件事也是排空队列。
- 分片数建议 = 物理核数减去业务池占用的份额，并且**从配置读**，不要硬编码（现有业务池是 10 条，8 核机器上 4 分片 + 10 业务线程已经超卖）。这两个数要能互相推导。

**交付物**：`Shard` 类、分片配置（分片数、每分片连接上限）、分片启动/停止。

**指标**

- 单分片 1000 条连接、每分钟 1 次心跳流量时，线程 CPU 占用 < 1%。
- 单分片处理一轮事件的成本与事件数近似线性（1000 事件的一轮 < 1ms，不含业务）。
- 分片与业务池的线程总数不超过物理核数 × 1.5。

**验收**：M0 的压测客户端建 1000 条连接、只发心跳，观察分片线程 CPU 与内存曲线是否平直。

## M5 监听与接入 Listener

**为什么**

接入是一条独立的路径，它有自己的过载模式（连接风暴），必须和普通收发包分开处理。

**思想与做法**

- 监听 fd 只管 `accept`，通信 fd 只管收发，两者角色不混（这条原设计里已经写对了，保留）。
- `accept` 要**循环 accept 到 `EAGAIN`**，不是一次一个。LT 模式下一次一个虽然也能工作，但会把一次连接风暴摊成很多轮 `epoll_wait`。
- Linux 上优先用 `accept4(..., SOCK_NONBLOCK | SOCK_CLOEXEC)`，一次调用同时完成「接受 + 设非阻塞」，省掉两次系统调用，也避免「接受了但还没设非阻塞」的窗口。
- 新连接给哪个分片：按连接数最少的那个给（避免倾斜），或者按 fd 取模（简单但可能倾斜）。**不要**在监听线程里做任何可能阻塞的事。
- 过载处理：连接数达到上限、`EMFILE`/`ENFILE` 时不能闷掉，要记录并在这段时间内暂停 accept（经典的「预留一个空闲 fd」技巧可以在需要时用上）。
- 可选优化（记在案，不一定要做）：`SO_REUSEPORT` + 每个分片各持一个监听 fd，内核直接分流。这样连「把 fd 交给别的分片」这个动作都省了。代价是负载均衡由内核哈希决定。

**交付物**：`Listener` 类、分片选择策略、连接数上限与过载统计。

**指标**

- 空载下 10 秒内建立 10000 条连接不丢（`backlog` 与 fd 上限都要够）。
- 达到连接上限后，服务器不崩、不死锁、能继续为已有连接服务，且有明确日志。
- accept 路径不产生额外线程唤醒（新 fd 注册进分片的 Poller 后，数据到达时自然会唤醒分片）。

**验收**：用压测客户端做「建 10 万条连接、立刻断开、循环」的冲击测试，观察是否泄漏 fd、是否出现 accept 卡死。

## M6 收包、拆帧、背压

**为什么**

TCP 不保证消息边界，粘包半包是常态而不是异常。同时这里是「灌爆内存」和「被慢连接拖死」的第一道闸门。

**思想与做法**

- 拆帧复用项目里已有的 `FrameCodec`（`include/protocol/FrameCodec.h`）：它已经处理了粘包、半包、非法帧丢缓冲，帧格式是 8 字节包长 + 4 字节指令长 + 指令 + protobuf 数据，上限 16MiB。这一层不需要重写。
- 拆帧留在**分片线程**做，不丢给业务线程——读缓冲是分片独占的，跨线程传半帧没有意义。
- 一次 `recv` 可能拿到半帧、一帧、多帧，所以是「读一次 → 循环拆帧直到 `NeedMoreData`」。
- **背压三件套**，缺一不可：
  1. 读侧：拆出一整帧就摘掉该连接的读关注（一条在飞）。这同时解决保序、背压、防灌爆三件事，原设计判断正确。
  2. 帧侧：包长字段不可信，超过上限直接断开（`FrameCodec` 已实现）。
  3. 写侧：写缓冲设硬上限，超过就断开该连接（M7 的慢消费者防护）。
- 每个连接初始分配小的读缓冲，按需增长，上限 = 一帧的最大值。不要让每个连接一上来就占 16MiB。

**交付物**：分片内的收包循环、每连接读缓冲管理、断开策略（含错误码分类：对端关闭 / 拒绝 / 超时 / 非法帧）。

**指标**

- 半包、粘包、一帧拆成 N 次到达、一次到达 N 帧、包长非法、指令长度非法，六类用例 100% 通过。
- 单条连接在小包（200B）下「一次 `recv` 拿到完整一帧」的比例 ≥ 95%（这是衡量读缓冲与收包策略是否合理的一个实用指标）。
- 被恶意灌帧时，进程内存有上界（= 连接数 × 上限），不随攻击持续时间增长。

**验收**：单元测试覆盖上述六类用例；再用一个「只发不发完」的客户端打一万条半包连接，观察内存与超时清理。

## M7 业务派发与回包

**为什么**

这是「框架开销」最集中的一段，也是 75% 这个指标真正被拉开差距的地方。

**思想与做法**

- 派发内容是一个自包含的小结构：`{连接标识, 完整帧字节}`。业务线程拿到它就能干活，不需要回读任何连接状态。
- **一条在飞**：分片在把帧投出去的时候就已经摘掉了读关注，所以同一个连接同时最多只有一个请求在飞。这带来三个好处：天然保序、任务队列深度天然被限制在「连接数 × 1」、突发流量不会把队列撑爆。这是本设计最值得保留的性质。
- 恢复读关注的时机是**写缓冲清空**，不是「响应开始发」（原设计判断正确，保留）。
- 业务侧分两步走，接口保持一致，先跑通再优化：
  - **M7-a（先用）**：直接投进现有的 `TaskQueueLoop`。它已经有 10 条线程、有延迟能力、有阶段自检。代价是每请求固定开销偏大（实测：这台机器上单生产者约 18 万条/秒、8 生产者约 56 万条/秒，即每次派发 1.8~5.4µs）。对 5 万 QPS 以内的业务量完全够用。
  - **M7-b（以后再说）**：换成一个轻量的业务池（POD 任务 + 环形队列 + 无锁或细粒度锁）。换的时候只换派发口实现，不改调用方——这正是「依赖倒置」的意义。
- **响应回投**：业务线程把「连接标识 + 字节」放进**该连接所属分片**的待发送队列（加锁），然后只做一件事：唤醒那个分片。分片把字节倒进写缓冲、关注可写。
- 慢消费者防护：写缓冲超过上限 → 断开。对端只收不读时，服务器不能跟着吃内存。
- **指令分发用注册表，不用反射**（这是你已经决定的方向，这里把接口定死，方便 M10 之前就接上）：

  | 表项字段 | 作用 |
  | --- | --- |
  | 指令名 | 与协议里的指令字段一致 |
  | 解析函数 | 用**生成的 message 类**（`build/generated` 里已有）做 `ParseFromArray`，不是 `DynamicMessage` |
  | 处理函数 | 业务逻辑，入参是解析好的具体类型 |
  | 组装函数 | 把响应 message 序列化成字节 |

  注册发生在启动期（一条新指令 = 一个 `.proto` + 一处注册），注册完成后表**只读**，热路径查表不需要加锁。指令名 → 表项的映射也在启动期建好，热路径只做一次查表。

**交付物**：派发口（分片 → 业务池）、回投口（业务池 → 分片）、待发送队列、`CommandRegistry`。

**指标**

- 保序：同一连接连续发 1000 个请求，响应顺序 100% 与请求一致。
- 派发 + 回投的固定开销占单请求总耗时的比例 < 10%（业务耗时 100µs 时）。
- 查表 + 解析的开销：小消息 < 1µs。
- 写缓冲有硬上限，慢消费者连接被断开且记录原因。

**验收**：压测客户端做「单连接顺序打 1000 个请求」的保序测试、「100 条连接并发打 10 万请求」的正确性测试、「一条连接只连接不读」的慢消费者测试。

## M8 定时器与超时

**为什么**

没有超时，一台只发半包、或者只收不读的客户端就能永久占住一条连接。原设计里把超时留给了「上层处理」，实际上超时就该在这一层做掉。

**思想与做法**

- 三类超时，都要有：**半包超时**（收到一部分帧之后再没动静）、**空闲超时**（整条连接长时间没有完整交互，心跳可以刷新它）、**写超时**（写缓冲长时间没发完）。
- 结构用「最小堆 + 到期时刻」就够，不需要复杂的时间轮。分片持有一个定时器堆，插入 O(log n)，每轮取最近到期时间。
- **`epoll_wait` 的超时参数 = 最近一个定时器到期时刻**，所以分片循环永远不会永久阻塞（这也是为什么 M1 的接口必须带超时参数）。
- 定时器回调里只做「标记 + 交给清理阶段」，不要在回调里直接销毁连接（会踩到正在遍历的数据结构）。
- 定时器精度要求不高（百毫秒级），不要为了精度去牺牲吞吐。

**交付物**：`TimerQueue`、三类超时的挂载点、超时统计计数。

**指标**

- 定时器精度 ±10ms 以内（百毫秒量级超时下）。
- 100 万个定时器插入/取消，耗时与 log(100 万) 呈线性关系。
- 半包连接在超时后 2 秒内被回收。

**验收**：专门写一个「打半包就断」的客户端，观察连接数在超时后回落；同时观察进程 fd 数回落。

## M9 关闭与优雅停机

**为什么**

「能跑起来」和「能停下来」是两件事。停机阶段是 use-after-free、fd 泄漏、请求丢失的高发区。

**思想与做法**

- 信号处理：Linux/macOS 上忽略 `SIGPIPE`（或统一用 `MSG_NOSIGNAL`），处理 `SIGINT`/`SIGTERM` 走优雅停机流程。Windows 走控制台事件。
- 停机顺序（顺序不能变）：① 停止 accept ② 等待在飞请求归零（设一个上限时间）③ 排空写缓冲 ④ 停止分片 ⑤ 停止业务池 ⑥ 关闭监听 ⑦ 上报最终统计。
- 每个阶段都要能被 `status` 命令观测到（接入 `ShineBasicModule` 的阶段自检），停机卡在哪一步要能一眼看出来。

**交付物**：停机流程、`--service` 模式下的信号处理、最终统计上报。

**指标**

- 停机时在飞请求要么收到完整响应，要么收到明确的断开，没有「发了一半」的帧。
- 退出前 fd 数归零、线程数归零。
- 重复启动-停止 100 次不泄漏、不崩溃。

**验收**：压测运行中直接发停机信号，检查客户端收到的响应完整性、进程退出码、fd 与线程统计。

## M10 基准、分段计时与调优

**为什么**

「够不够 75%」只能靠数字回答。这一步也是唯一允许动性能的地方。

**思想与做法**

- 用 M0 的脚手架跑第 1 节的四组条件（消息大小 × 业务耗时 × 连接数），输出吞吐、单核效率、p50/p99/p99.9。
- 用分段计时看瓶颈落在哪一段：拆帧段高 → 看缓冲与拷贝；入队段高 → 看业务池结构与分片；send 段高 → 看写缓冲与合并；`epoll 返回 → recv` 段高 → 看事件批量与唤醒。
- 按这个顺序做优化（收益从大到小），每做一项都重跑基准：
  1. **业务池队列拆分**（当前 `TaskQueueLoop` 是单队列 + 单把锁 + 10 条线程共享）。这一步在本次评审后已经先做了「一次入队只唤醒一个人」，剩下的队列拆分留在这里做。
  2. **缓冲与拷贝**：每连接缓冲复用、帧解析少一次拷贝、派发结构避免多次内存分配。评审里已经记下这一项，等基准证明它值钱再动。
  3. **`epoll_ctl` 收敛**（见第 6 节，属于未来决策）。

**指标**

- 第 1 节的每一组条件都有可复现的数字，且连续两次运行偏差 < 5%。
- 相对对比框架达到约定的比例（默认 75%），且 p99 不劣化。
- 在业务耗时 100µs 的档位上，框架开销占比 < 20%。

**验收**：基准报告 + 分段计时报告各一份，能指出下一次优化该动哪一段。

## 4. 跨线程唤醒专项设计

### 4.1 要解决的问题

分片线程在 `epoll_wait` 里睡着，业务线程算完了要它起来干活。分片线程不是在等锁，而是在等内核事件——**条件变量叫不醒一个阻塞在 `epoll_wait` 的线程**，这是本架构最容易踩的硬坑。

### 4.2 做法：给每个分片配一个「能进 Poller 集合的通知对象」

思路是：不要试图「叫醒线程」，而是「让线程等待的那个东西自己变得可读」。这样它和普通 IO 事件走同一条路径，不需要第二套等待机制。

| 平台 | 通知对象 | 写（通知方） | 读（分片） |
| --- | --- | --- | --- |
| Linux | `eventfd(0, EFD_NONBLOCK \| EFD_CLOEXEC)` | 写 8 字节整数（累加计数） | 读 8 字节一次排空 |
| macOS（kqueue） | `EVFILT_USER` | `kevent` 触发 | kevent 事件，无需读 |
| macOS（poll 兜底） | `socketpair(AF_UNIX, SOCK_DGRAM)` | `send` 1 字节 | 循环读到 `EAGAIN` |
| Windows | 回环 UDP socket（或 TCP 环回对） | `sendto` 1 字节 | 循环读到 `WSAEWOULDBLOCK` |

关键点：**Windows 上没有 eventfd，`WSAPoll` 也只能等 socket**，不要试图把 `CreateEvent` 塞进去。回环 UDP 是最省事的等价物。

### 4.3 三条必须遵守的规则

1. **通知方只在「队列由空变非空」时写**。判定必须在队列锁内完成（`push` 后队列长度 == 1 才通知）。这样 N 条响应在分片忙碌期间到达，只会产生 1 次唤醒写，而不是 N 次。
2. **分片被唤醒后必须一次排空**。读循环读到 `EAGAIN` 为止，否则 LT 模式会反复触发同一个事件，变成忙等。
3. **通知对象和普通 fd 一样，注册进 Poller 一次，长期有效**（不要每次唤醒都注册/注销）。

### 4.4 什么时候需要唤醒

| 场景 | 需要唤醒吗 | 说明 |
| --- | --- | --- |
| 业务线程回投响应 | 需要 | 唯一的高频路径，必须合并通知 |
| 外部线程要求断开某条连接（管理命令） | 需要 | 低频 |
| 新连接交给分片 | 通常不需要 | fd 注册进 Poller 后，数据到达时内核自然唤醒分片；只有需要立刻主动发包（如打招呼）时才唤醒 |
| 定时器 | 不需要 | 定时器归分片自己管，`epoll_wait` 的超时参数就够了 |

### 4.5 反模式（这几条都不要做）

- 用 `sleep` + 轮询队列当唤醒机制：延迟由睡眠粒度决定，CPU 白烧。
- 用很短的 `epoll_wait` 超时（比如 1ms）当「近似唤醒」：空闲时也会每秒醒 1000 次，1000 条连接下 CPU 直接被打满。
- 每条响应一次唤醒写，不做合并：唤醒本身变成系统调用放大器。
- 唤醒判定放在队列锁之外：会丢唤醒，表现为「偶尔某个请求永远不回」。

### 4.6 指标与验收

- 丢失唤醒次数 = 0（连续 100 万次唤醒压测）。
- 唤醒延迟 p50 ≤ 20µs、p99 ≤ 100µs（Linux）。
- 空闲分片（只有心跳）CPU 占用 ≈ 0%。
- 合并率可观测：同一分片在忙碌窗口内的「响应数 ÷ 唤醒次数」应明显大于 1。

## 5. 平台差异矩阵

| 项 | Linux | macOS | Windows |
| --- | --- | --- | --- |
| 事件等待 | `epoll`（LT） | `poll` 兜底，`kqueue` 留扩展 | `WSAPoll` |
| 通知对象 | `eventfd` | `EVFILT_USER` / `socketpair` | 回环 UDP socket |
| 句柄类型 | `int` | `int` | `SOCKET`（不是 int） |
| 非阻塞 accept | `accept4` | `accept` + `fcntl` | `accept` + `ioctlsocket` |
| 屏蔽 SIGPIPE | `MSG_NOSIGNAL` | `SO_NOSIGPIPE` | 无此问题 |
| fd 上限 | `RLIMIT_NOFILE`（默认常为 1024，必须查） | `RLIMIT_NOFILE` | 无此限制，用 `FD_SETSIZE` 之外的概念 |
| 对端关闭的可靠判定 | 可读 + `recv` 返回 0 | 同左 | WSAPoll 的 `POLLHUP` 不可完全信赖，用「可读 + `recv` 返回 0」兜底 |

## 6. 未来决策点（记在案，现在不做）

以下每一项都会改动热路径，必须先用 M10 的基准证明它值钱，再决定做不做。

1. **`epoll_ctl` 收敛**。当前「一条在飞」用摘/挂读关注实现，一个请求要 3 次 `epoll_ctl`（摘读、挂写、恢复读）。可能的替代：用 `EPOLLONESHOT`（事件触发后自动摘除，省一次 MOD）；或把「一条在飞」从 fd 兴趣位挪到连接状态位（读循环只读到一帧就停，剩余字节留内核缓冲），只在真正需要背压时才摘读关注。收益量级 1~3µs/请求，业务耗时 100µs 以上时可以忽略。
2. **缓冲与拷贝**。每连接缓冲复用、帧解析借视图而不是 `assign` 出新的 `std::string`、派发结构避免每次 `unique_ptr` 分配。当前实测派发路径每次 1.8~5.4µs，其中相当一部分是分配。
3. **业务池队列拆分**。单队列 + 单锁 + 10 线程共享，改成每线程队列或分片队列。本次已完成「一次入队只唤醒一个线程」，队列结构拆分留到基准需要时。
4. **`SO_REUSEPORT` 每分片独立监听**，省掉 fd 跨线程交接。
5. **ET 模式 + 读预算**。ET 性能更好但必须读空，和「一条在飞」的语义有冲突，只有在证明 LT 的额外轮次真的成为瓶颈时才考虑。
6. **UDP / TLS / 每连接加密**：目前不在范围内。

---

## 7. 已完成的前置改动（本次评审后落地）

1. `ThreadPool` 的入队唤醒从「全员唤醒」改为「只唤醒一个」，并单独提供退出用的全员唤醒（`wakeAll`）。
2. `ThreadPool` 的管家线程循环从「先睡再判断」改为「先判断再睡」，少一次无谓睡眠和一轮重复判断。
3. `ThreadPool` 初始化加了重复初始化保护；管家线程执行体加了异常兜底（执行体抛异常不再会静默杀死一条线程）。
4. 验证程序：`build/_threadpool_check.cpp`（一次性检查，不进构建系统）。实测结果：20 万条任务无丢失；8 生产者并发约 56 万条/秒；睡下后单条唤醒最差 1.5ms（Windows 条件变量实现，Linux 上应由 M2 的唤醒器把这个数压到 20µs 级）；延迟任务不提前执行。

## 12. 交接清单（给中途接手的人或 Agent）

**接手前必读**：第 2.3 节并发铁律、第 3 节（连接状态机）、第 4 节（唤醒设计）。这三处是这套架构里「做错了会偶发、难复现」的全部位置。

**当前状态**：网络层尚未开始（M0 未开工）。已有的可复用资产：`FrameCodec`（粘包半包已实现）、`ThreadPool` + `TaskQueueLoop`（业务池，已修好唤醒风暴）、`ShineBasicModule` 自检体系、`proto/` 与生成的 message 类。

**下一步做什么**：按 M0 → M1 → M2 顺序，不要跳。M0 的基准脚手架必须先有，否则后面所有性能决定都只能靠猜。

**明确不要做的事**：

- 不要用 `ThreadPool` 直接当分片线程（原因见 M4）。
- 不要在业务线程里碰 socket、连接对象或 fd。
- 不要用 fd 号当连接标识。
- 不要在热路径上用 `DynamicMessage` / 反射解析 protobuf（用生成类 + 注册表）。
- 不要为了性能提前做第 6 节里的任何一项。

**验收怎么跑**：每个里程碑的「验收」小节都写明了可执行的验证方式；`build/_threadpool_check.cpp` 是线程池侧的可复现验证样例，可以照它的形式写网络层的验证程序（放在 `build/` 下，不进版本库）。

**术语表**

| 术语 | 含义 |
| --- | --- |
| 分片（Shard） | 一条线程 + 一个 Poller + 约 1000 条连接，连接的独占所有者 |
| 一条在飞 | 同一连接同时只有一个请求在处理中；实现方式是摘掉读关注 |
| 唤醒器（Wakeup） | 每个分片持有的、能进 Poller 集合的通知对象 |
| 背压 | 通过摘读关注、写缓冲上限、连接数上限，让压力在源头停住而不是堆在内存里 |
| 分段计时 | 把一次请求拆成 6 段分别计数，用于定位瓶颈 |
