## 0. 为什么会有这份文档

设计文档是**目的地地图**：它写全了 11 个里程碑、每个里程碑的指标和验收。它写得全是对的（它还要负责「中途交给 AI 也能接手」这件事），但**全**恰恰是它不能当路线用的原因——一份列了 11 个里程碑的文档，没法告诉你下一行代码写什么。

具体卡住的机制有三个，都不是能力问题：

1. **每一步里同时有太多「决定」和太多「未知」**。比如 M0 第一步就要你想清楚目录怎么分、统计容器长什么样、压测客户端怎么设计——四五个决定叠在一起，就动不了了。
2. **第一阶没有任何可见反馈**。M0 是脚手架（空目录、空类、统计），做完看不见任何东西跑起来，这是最容易死在里面的一步。
3. **顺序不对**。设计文档的顺序是「一次就做对」，那需要经验；学的时候应该「先跑起来，再改造成那个形状」。

顺便说一句证据：这个项目里你已经做出来的东西——策略模式注入的线程池、图结构的任务编排 `dependOn/then`、带借条和归还语义的数据库连接池、还有那次 `getStage()` 返回引用的竞态修复——论难度都在「accept 一个 socket 然后回显」之上。所以这里不是能力问题，是**排序**问题。

## 3. 第 A1 阶：阻塞式 echo 服务器（已完成）

### 目标

一个程序：监听 `127.0.0.1:9000`，接受第一条连接，收到多少字节就原样发回去，对端关闭后干净退出。

**这一阶只处理一条连接就够了。**不要为了「以后多条连接」提前设计任何东西。

## 4. 第 A2 阶：单文件 echo 客户端（已完成）

### 目标

连 `127.0.0.1:9000`，发 N 条消息，每条都要完整收回来并逐字节比对；最后打印成功数、失败数、耗时、QPS；
只要有一条失败就以非 0 退出。

命令行：`stepA2_echo_client [条数] [消息内容] [端口] [主机] [-v]`，默认 `1000` / `hello` / `9000` / `127.0.0.1`。
消息内容写成 `#5000` 表示 5000 个 `a`，测大消息不用在命令行里敲长字符串；`-v` 逐条打印 send/recv 各调用了几次。

## 5. 第 A3 阶：每条连接一个线程的服务器（已完成 2026-09-22）

### 目标

监听 `127.0.0.1:9000`；接受一条连接就把它的回显循环交给一条独立的线程；多条连接**同时**被服务，
互不影响（A1 一次只伺候一条）。

### 必要的注意事项

1. **落地位置**：和 A1 同一个口径，直接在框架里做的——`src/network/Net.cpp` 的 `run()` 现在是
   「`accept` 之后把这条连接的 `recv`→`send` 循环打包成 `Task<std::any>` 丢进 `TaskQueueLoop`，
   然后立刻回去 `accept`」。连接 socket 归那个任务独占，任务收工时自己 `closesocket`。
2. **线程数的预设值在 `TaskQueueLoop`**（`kTaskThreadCount`，当前 10）。`ThreadPool` 的线程数已经从
   编译期常量 `THREADNUM` 改成构造参数（`_threads` 从 `array` 改成 `vector`）；要多给连接就调这个数。
3. **并发上限 = 预设值 − 1**：`net->run()` 的 accept 循环本身也是一个池任务，常驻占着 1 条线程，
   所以 10 条线程实际只留 9 条给连接。实测：挂住 8 条空闲连接时新客户端照常跑完，挂住 9 条时新客户端
   连得上但一条回显都拿不到（在排队等线程）。
4. **这 10 条线程是框架共用的**：延迟消息、连接池维护、以后的业务都在这上面排队；连接任务阻塞在
   `recv` 里占的是所有人的线程。这是 A6 要换掉它的直接原因（设计文档 M4、§2.3 铁律 6）。
5. **`send` 带 `MSG_NOSIGNAL`**（已经加了）：客户端异常断开时的 SIGPIPE 就在这条路径上。
6. 这一阶是**对照物**，B 阶段按 M4 换成分片时不带过去：分帧、背压、超时都用正确的形状在后面做，
   别在这条路上继续加功能。

（2026-09-22 实测记录：单客户端 1000 条全成功；两个客户端同时跑 300 + 300 条全成功，服务端日志里
两种消息长度交错切换 427 次——串行执行只会是 1 次；33 次「接受连接」对应 33 次「收到 0 字节，对端关闭」，
之后服务器仍能继续服务。）

## 6. 第 A6 阶：换 `epoll`，一条线程管 1000 条连接

### 这一阶的位置（为什么）

A3 的形状是「每条连接占一条池线程」：1000 条连接它**都收得下**（实测 3.1 秒全连上、全断开后 fd 回到 6、
空闲时 CPU 0.6%），但**同时只能服务 9 条**（10 条池线程减去 accept 循环自己那条）——实测 15 条连接
各发一次 `hello`，只有 9 条拿到回显。

这一阶要的形状完全不同：**一条线程 + 一个 `epoll` 集合 + 每连接一点状态**，管住全部连接。

原计划里的 A4（非阻塞 + `sleep` 忙等）和 A5（`poll` 换掉忙等）并进这一阶：不安排「故意写笨办法、
感受代价」的中间态了，但那两阶的技术点一个都不能少——顺序展开在下面「必须按这个顺序做」里。
原计划还让先读 `tests/reactor_demo.cpp`（非阻塞 + `poll` + 读写缓冲 + 干净关闭），那份参考实现从来没提交过，
现在也不补了：这一阶本来就是照那个形状把 `epoll` 版写进框架，形状已经落在 `src/network/Net.cpp` 的
`ConnPoller` / `ConnShard` 里，实现记录见 §6.1。

### 目标

一条线程（`Net::run()` 那条）管 1000 条连接：

- 1000 条连接建立后稳定保持，空闲时进程 CPU ≈ 0；
- 任何一条连接发 `hello` 都收得到 `hello`（不是只有前 9 条）；
- 客户端正常关闭、异常断开（RST）、只发一半（半包）都不影响其它连接；
- 全部关闭后 fd 数回落到基线附近（不泄漏）。

### 必须按这个顺序做（每一步都能单独跑出结果）

1. **先把非阻塞落到单条连接上**：连接 socket 设非阻塞；`recv` 的 `EAGAIN` 不当错误；`send` 部分发送
   要记游标。先让 A2 客户端 1000 条跑通——这一步的产物是「语义对了」，还不需要 `epoll`。
2. **监听 socket 也非阻塞**，`accept` 循环接到 `EAGAIN` 为止（Linux 上 `accept4(..., SOCK_NONBLOCK)`
   一次搞定）。漏了这条，第 6 步连接数一上来就会卡在 `accept` 上。
3. **连接表 + 每连接状态**：`unordered_map<int, Connection>`（`std::vector` 也行）。每条连接至少要有：
   socket、还没发完的字节、发到哪儿了（游标）、以及「这条连接是谁」的标识。
4. **接上 `epoll`（LT 模式）**：`epoll_create1` → `epoll_ctl(ADD/MOD/DEL)` → `epoll_wait`。
   到这一步你才真正拥有「一条线程管 N 条」。
5. **事件语义四件事**（这一阶的核心，写错了不是忙等就是丢连接）：
   - 常挂 `EPOLLIN`；**`EPOLLOUT` 只在「还有字节没发完」时挂，发完立刻摘**（一直挂着，`epoll_wait`
     每次都告诉你可写，等于自己造了个忙等）；
   - `epoll_wait` 返回 `-1` 且 `errno == EINTR` 要重试；
   - 可读事件里 `recv` 返回 0 就是对端关闭（`EPOLLRDHUP` 只是提示，最终以 `recv` 的返回值为准）；
   - 注册时的 `data` 里放**连接标识**，不放裸 fd（fd 会被内核复用）。
6. **压到 1000 条**：先看资源上限（`ulimit -n` 本机是 524288，够；`listen` 的 backlog 顺手调大），
   再用 `python3 tools/netbench/hold_conns.py 1000 60` 保持 1000 条，另开终端看 CPU、fd、内存。

### 这一阶真正要学的三件事

1. **poller 的事件语义与事件循环**：怎么加、怎么删、怎么等、事件回来怎么分派给「哪条连接」；
   什么时候挂 `EPOLLOUT`、什么时候摘。
2. **非阻塞读写与半包**：`EAGAIN` 不是错误；一次 `recv` 不保证是一个完整消息；`send` 会部分成功——
   「收到的字节」和「没发完的字节」是两份独立状态。
3. **连接生命周期与线程归属**：只有这条事件循环线程能碰连接；连接的删除只能放在一轮事件处理**结束之后**
   （遍历中途删就是经典的 use-after-free）。

### 这一阶不许做的事

- 不许再用 `TaskQueueLoop` / 任何额外线程来管连接（这一阶的主题就是「一条线程管 N 条」）
- 不许用 `select`（同一件事的旧写法，学不到新东西）
- 不许改量尺：`build/bin/stepA2_echo_client`、`tools/netbench/hold_conns.py`
- 不许一步到位：按上面 6 步走，每步都能单独跑出结果
- 这一阶不做：分帧（C1）、业务派发（C3）、唤醒器（C4）、定时器（C5）、优雅停机（C6）

### 需要的判断依据（不给代码，只给判断标准）

- 三个调用的分工：`epoll_create1` 建集合、`epoll_ctl` 增删改、`epoll_wait` 等事件；
  `epoll_wait` 的返回值是「这次有几个事件」，可能小于你给的上限。
- **`EPOLLIN` 表示「可读」，不代表「有数据」**：可能是对端关了。可读永远要配合 `recv` 的返回值判断。
- 写缓冲：非阻塞 `send` 的返回值是实际发出去的字节数，可能是 0（发送缓冲满）。剩下的字节要留着等 `EPOLLOUT`。
- 空闲 CPU 不为 0 时，按这个顺序查：① `EPOLLOUT` 是不是常挂 ② `epoll_wait` 的超时是不是给了 0
  ③ 是不是在写缓冲为空时还在反复 `send`。
- 这一阶只做 Linux（`epoll` 是 Linux 的）。跨平台抽象是 B1 的事，别在这儿顺手封接口。

python3 tools/netbench/edge_cases.py                                      # RST / 半包 / 粘包 / 大消息 / 复用

### 验收（五条）

1. `stepA2_echo_client 1000 hello` 全成功、退出码 0。
2. `hold_conns.py 1000 60`：1000 条全部连上并保持住，期间没有被断开；空闲时那条线程 CPU ≈ 0
   （是「接近 0」，不是「不高」）。
3. `hold_conns.py 1000 0 --echo`：1000 条各发一次**全部成功**（A3 只能过 9 条——这就是这一阶的意义）。
4. 全部断开后 fd 回落到基线附近；客户端被突然杀掉（RST）不影响其它连接。
5. 你能说清：`EPOLLOUT` 什么时候挂、什么时候摘；「可读」为什么不能直接当成「有数据」。

### 故障对照表

| 现象 | 最可能的原因 |
| --- | --- |
| 空闲连接时 CPU 一直 100% | `EPOLLOUT` 常挂；或 `epoll_wait` 超时给了 0；或写缓冲空了还在死循环 `send` |
| 只有前几条连接有回显 | 还是 A3 的形状（池子/线程）；或 accept 只接了一个；或事件没按连接标识分派 |
| 连接一多就不接新连接了 | 监听 socket 没非阻塞、卡在 `accept` 上；或 backlog 太小 |
| 客户端断开后进程 CPU 升高 | 对端关闭那条路没把连接从 `epoll` 和连接表里删掉，之后每轮都在它身上转 |
| 偶发崩溃 / 数据错乱 | 连接对象在一轮事件遍历中途被删；或 `data` 里放的是裸 fd，fd 被复用后认成了别的连接 |
| 只收到一半回显 | 非阻塞 `send` 部分成功，剩下的没等 `EPOLLOUT` 就丢了 |
| 压到 1000 条时 `accept` 报 `EMFILE` | fd 上限（`ulimit -n`）不够，或连接关了没摘 fd |
| 1000 条里只有几百条连上 | `listen` 的 backlog 太小、或者 accept 循环没接到 `EAGAIN` |

## 6.1 A6 实现记录（2026-09-22）

### 落地位置与形状

全部在 `src/network/Net.cpp` 里，`Net::run()` 自己跑事件循环（借 `TaskQueueLoop` 的一条后台线程常驻，
不再是「一条连接一个池任务」）。三个匿名 namespace 里的东西：

| 名字 | 干什么 |
| --- | --- |
| `Connection` | 一条连接的状态：socket、收到的字节、没发完的字节 + 发送游标 |
| `ConnPoller` | 事件集合的薄封装：`init/add/modify/remove/wait`。**Linux 走 `epoll`（LT），Windows 走 `WSAPoll`**，上层代码一套 |
| `ConnShard` | 事件循环本体：accept 到 EAGAIN、读写分派、EPOLLOUT 挂摘、一轮结束后的清理阶段 |

`Net.cpp` 里另有三个跨平台小工具：`setNonBlocking`、`isWouldBlock`（`EAGAIN`/`WSAEWOULDBLOCK`）、
`pollNative`（Windows 上 UCRT64 连 `<poll.h>` 都没有，必须走 `WSAPoll`）。

### 六个步骤的实际顺序

1. 连接 socket 非阻塞 + `EAGAIN` 处理 + 发送游标；监听 socket 非阻塞（顺手在 `createAcceptSocket()` 里做了）。
2. `accept` 循环接到 `EAGAIN` 为止。
3. 连接表 `unordered_map<SocketType, Connection>` + 每连接状态。
4. `epoll_create1` / `epoll_ctl(ADD/MOD/DEL)` / `epoll_wait`（LT）。
5. 事件语义四件事：`EPOLLOUT` 只在有积压时挂、发完立刻摘；`EINTR` 重试；`recv` 返回 0 才算关闭；
   注册时 `data.ptr` 放连接标识而不是裸 fd。
6. 压到 1000 条。

**修掉的三个原有问题**（都在改之前挡住路）：

- `startUp()` 里那段「调整为非阻塞」引用了不存在的变量 `fd`（Linux 分支根本编不过），而且把失败判断写反了
  （`if (flags == -1)` 里才去调用 `F_SETFL`）；
- `accept` 失败后无条件 `continue`：监听 socket 一旦非阻塞，这就变成纯忙等（CPU 100%）；
- `listen` 的 backlog 是 128，压 1000 条连接时会有一批连不上。

### 实测（Windows 11 / MSYS2 UCRT64 / g++ 16.2.0，`tools/netbench/run_acceptance.ps1` 一键复现）

| 量尺 | A3 形状（改之前） | A6（一条线程 + 事件集合） |
| --- | --- | --- |
| `stepA2_echo_client 1000 hello` | 1000/1000 | **1000/1000**，QPS ≈ 5.4 万 |
| `hold_conns.py 15 0 --echo` | 9/15 | **15/15** |
| `hold_conns.py 1000 0 --echo` | 9/1000 | **1000/1000** |
| `hold_conns.py 1000 10` | — | 1000 条全部连上（0.08 秒）、保持 10 秒、0 条被断 |
| 句柄回收 | — | 基线 144 → 1000 条时 900+ → 全部断开后**回落到 144** |
| 空闲 CPU（5 秒采样） | 0.6%（A3 记录） | **0 ~ 16 ms / 5 秒**（≈ 0.3% 以内） |
| 边界：RST / 半包 / 粘包 / 5000 字节 / 复用 | — | 5 项全过（`edge_cases.py`） |

### Linux 侧待复验（下一件事）

今天这台是 Windows，走的是 `WSAPoll` 分支（功能对，但它是 O(N) 的，无法体现 `epoll` 的价值）。
**真正的 `epoll` 分支（`#else` 那半边）还没在 Linux 上编译运行过**，因为 `epoll` 是 Linux 独有的。
到 WSL 或 Linux 机器上要做的就三件：

```bash

INKING_AUTO_NETWORK=1 build/bin/InkingBackendFramework &
build/bin/stepA2_echo_client 1000 hello
python3 tools/netbench/hold_conns.py 1000 0 --echo --timeout 5
python3 tools/netbench/edge_cases.py
# 另开终端看：top -H -p <pid>（只应有一条线程热，空闲 ≈ 0）、ls /proc/<pid>/fd | wc -l（全关后回落）
```

预期：与上表同结果。若 Linux 上编不过，最可能的点已经收拢在 `ConnPoller` 这个类里
（`epoll_event.data.ptr`、`EPOLLRDHUP`、`nfds_t` 这几处），改起来是局部改动。

### 这一阶留下的技术债（按文档，属于后面几阶）

- `ConnPoller` 是私有的临时封装，B1 会把它抽成正式的 `Poller` 接口；
- 还没做：分帧（C1）、连接状态机与「一条在飞」（C2）、业务派发（C3）、唤醒器（C4）、
  定时器与超时（C5）、优雅停机（C6）；
- `epoll_wait` 的超时暂时固定 1000ms；C5 里它必须变成「最近一个定时器到期时刻」；
- Windows 分支的 `remove()` 只是把 `pollfd` 标记成无效槽位，`_descriptors` 会随历史连接数单向增长
  （Linux 没有这个问题）。B1 抽接口时一并处理。

## 6.2 B 阶段实现记录（2026-11-04，B1+B2+B3 一次做完）

### 落地位置与形状

A6 那套东西原来全挤在 `Net.cpp` 的匿名 namespace 里（`Connection` / `ConnPoller` / `ConnShard`）。
B 阶段把它拆成了「一层一件事」，每一层单独一个文件：

| 文件 | 干什么 | 对应设计文档 |
| --- | --- | --- |
| `include/network/SocketOps.h` + `src/network/SocketOps.cpp` | 平台语义收口：句柄类型、非阻塞、`wouldBlock`、发送标志、关闭 | M1 交付物 |
| `include/network/Poller.h` + `src/network/Poller.cpp` | `Poller` 接口 + `EpollPoller` / `PollPoller` 两个实现 | M1 |
| `include/network/Wakeup.h` + `src/network/Wakeup.cpp` | 唤醒器（回环 UDP 自投递） | M2 |
| `include/network/Connection.h` | 连接状态 + 读写缓冲 + 状态机 | M3 |
| `include/network/Shard.h` + `src/network/Shard.cpp` | 一条线程 + 一个 Poller + 一批连接 + 交接队列 | M4 |
| `include/network/Listener.h` + `src/network/Listener.cpp` | 独立接入线程：循环 accept、挑分片、交接 | M5 |
| `include/network/NetworkStage.h` | 模块名 + 自检阶段编号（多处共用，抽出来防撞号） | — |
| `include/network/NetworkConfig.h` + `src/network/NetworkConfig.cpp` + `config/networkConfig.json` | 端口 / 分片数 / 每分片连接上限 | M4 交付物 |
| `include/network/Net.h` + `src/network/Net.cpp` | 门面：读配置、装配、按序启停 | — |

### 线程形状

```
主控（TaskQueueLoop 的一条后台线程）  Net::run()
  ├─ 接入线程 ×1   Listener   只 accept；按「当前连接数最少」挑分片
  ├─ 分片线程 ×N   Shard      各自一个 Poller + 连接表，互不共享任何状态
  └─ 业务线程池    TaskQueueLoop（本阶还没接，C3 才用）
```

一条新连接走的路径（**所有权只转交一次**）：

```
accept → setNoDelay / setNonBlocking → Shard::adopt(fd)
       → 交接队列 + 合并唤醒（队列由空变非空才写一次）
       → 分片线程 drainIncoming：入连接表 + 注册进 Poller → 从此只有这条线程碰它
```

关闭走的路径（**分两段，中间不许插别的**）：`markClosing()`（只置标记）→ 一轮事件处理完
→ 清理阶段 `Poller::remove` → `close` → 连接表 erase。顺序反过来就是摘错人。

### 与设计文档对不上的三处，以及理由

1. **唤醒器用回环 UDP，不用 eventfd。** 设计文档 §4.2 给 Linux 首选 `eventfd`。这里统一用
   「绑在 127.0.0.1 的 UDP socket，`sendto` 给自己」：三个平台一份代码、零 `#ifdef`，
   而且读端就是普通 fd，和连接走同一条注册路径。代价是每次唤醒多一次用户态拷贝；
   按「一条在飞 + 合并通知」的设计，唤醒次数远小于请求数，这个代价可以接受。
   Linux 侧的 `eventfd` 留作性能项，等 M10 基准证明值得再换。
   —— 这条决定的真正理由是：**本机没有 Linux，写一条没编译过的 `#ifdef` 分支是负债而不是优化。**
2. **acceptor 是独立线程**（设计笔记「还没定的事」第 2 条的三个选项之一）。理由是压测时
   「0 号分片比别的分片慢」会污染对分片均衡性的判断；代价是多一条线程、多一次交接。
3. **分片数进配置**（默认 4）。`NetworkConfig::describe()` 会把实际取值写进日志第一行，
   所以「当时按几核配的」事后能查。

### 实测（Windows 11 / MSYS2 UCRT64 / g++ 16.2.0，4 分片）

| 量尺 | A6（单分片） | B3（4 分片 + 独立接入线程） |
| --- | --- | --- |
| `hold_conns.py 1000 0 --echo` | 1000/1000 | **1000/1000**，建连 0.19~0.22 秒（4500~5300 条/秒） |
| `stepA2_echo_client 1000 hello` | 1000/1000，QPS 5.4 万 | **1000/1000，QPS 5.74 万** |
| `hold_conns.py 1000 15` | 1000 条全部保持 | **1000 条全部保持，0 条被断** |
| `edge_cases.py`（RST / 半包 / 粘包 / 5000B / 复用） | 5 项全过 | **5 项全过** |
| 分片峰值连接（退出时各分片自报） | — | **250 / 250 / 250 / 250**（1000 条，与「连接数最少」策略一致） |
| 句柄数（空闲 / 1000 连接 / 全断） | 144 / 900+ / 144 | **206 / 1206 / 206**（+62 是 4 个分片 + 接入线程各一个唤醒 socket 及其它新增阶段） |
| 停机 | kill（未验优雅退出） | **控制台 `exit`：退出码 0**，顺序为接入 → 分片 → 关监听，0 条 WARN/ERROR |
| 线程数 | 15 | **19**（4 分片 + 1 接入 + 业务池 10 + 控制台/日志侧） |

### 这一阶留下的债（按文档，属于后面几阶）

- **Linux `epoll` 分支仍未在 Linux 上编译运行过**（A6 遗留，B1 只是把它整体挪进了
  `Poller.cpp` 的 `EpollPoller`）。要复验的接口点已经收拢到一处。
- 连接的关闭是**硬关**：`markClosing` 之后直接 close，不排空写缓冲。优雅关闭属 C6。
- 连接上限到顶时直接拒绝新连接，没有用「预留一个空闲 fd」的技巧应付 `EMFILE`。
  也没做「暂停 accept 一段时间」的过载退避。
- 还没有定时器：`Shard` 里 `wait` 的超时固定 1000ms，C5 要把它改成「最近一个定时器到期时刻」。
- **echo 语义还在**：读到的字节直接进写缓冲。`Connection::receiveBuffer` 已就位但没有消费者，
  C1 接 `FrameCodec` 时改成「追加 → 循环拆帧 → 拆出一整帧才处理」。
- 每分片连接上限是「峰值判断」，不是「实时水位」：清理阶段之前被标记关闭的连接仍占一个名额，
  对上限 1000 的粒度没有影响，但如果以后要把上限调到很小的值，需要改成按 `_connections.size()` 判。

## 6.3 C1 实现记录（2026-11-04）

### 这一阶真正的变化：线上协议生效了

B3 的服务端是「收到多少字节回多少字节」，协议里根本没有「消息」这个概念。
C1 把它换成了：**字节进 `FrameCodec`，拆出一整帧才算一条消息**。

这带来一个必须说清楚的后果：**旧的验收脚本全部失效**。`hold_conns.py`、`edge_cases.py`、
`stepA2_echo_client` 发的都是裸字节，现在会被魔数判定挡在门口并断开——这不是回归，
是协议生效后的正确行为（端口扫描、错版本客户端本来就该在最短路径上被挡掉）。
它们保留在原处，脚本头部已注明「仅适用于 A6 时代」。C1 的验收改由新脚本
`tools/netbench/framed_client.py` 承担。

### 落点

| 位置 | 改动 |
| --- | --- |
| `include/network/Connection.h` | 新增 `FrameCodec codec`（每连接一份）；**删掉 `receiveBuffer`**——它和 codec 内部缓冲是同一件事的两个位置 |
| `src/network/Shard.cpp` | `readFrom` 改为「recv → `codec.push` → 循环 `next` 到 `NeedMoreData`」；新增 `consumeFrames` / `replyFrame` |
| `include/network/Connection.h` | 新增 `CloseReason` 与 `closeReason`：对端关闭 / 收错 / 发错 / 非法帧 / 慢消费者 |
| `src/network/Shard.cpp` | 断开原因分类计数；正常关闭写 `Trace`、异常写 `Warn`；退出时一次性打摘要 |
| `src/network/Shard.cpp` | 写缓冲上限 4 MiB（慢消费者防护，M6 背压三件套的第 3 件） |
| `tools/netbench/framed_client.py` | 新增：按帧打服务端，七类用例 |

### 三个判断，写下来免得以后反复

1. **每读一块就拆一遍，不是攒起来再拆。** 一个猛发 100 MiB 的客户端因此只能让缓冲长到
   一个 `recv` 块的大小；写成「读满再拆」的话，攻击面就是那 100 MiB。
2. **`receiveBuffer` 删掉，只留 `FrameCodec` 的缓冲。** 两份缓冲必须手工同步，漏一次就是半包丢失；
   而「未解析字节数」本来就等于 `codec.pendingBytes()`。
3. **慢消费者的判定口径是「原本就有积压，再加这一帧才超限」。** 这样单条大帧（最大 16 MiB）
   在缓冲为空时总能发出去，不会被上限误杀；而被杀的只有「一直发、从不读」的那种连接。

### 实测（Windows / MSYS2 UCRT64 / 4 分片，`framed_client.py`）

| 用例 | 结果 |
| --- | --- |
| 1000 条连接各发一帧并校验回显 | **1000/1000 逐字节相同** |
| 半包：一帧拆成三段、中间停 150 ms | **通过**，回显与请求一致 |
| 粘包：三帧一次 `write` | **通过**，逐帧收回 40 字节，顺序与内容一致 |
| 大包：5000 字节负载（超单次 `recv` 4096） | **通过**，5012 字节完整回显 |
| 非法帧 ×3：魔数不对 / 包长小于帧头 / 指令长超上限 | **三次都按预期断开连接** |
| 1000 条空连接保持 5 秒 | **1000/1000 仍在线** |
| 分片峰值连接 | **250 / 250 / 250 / 250** |
| 拆帧总数 | **1005** = 1000（echo）+ 1（半包）+ 3（粘包）+ 1（大包），与客户端发送数完全对上 |
| 关闭原因统计 | 对端 2003 / 非法帧 3 / 收错 0 / 发错 0 / 慢消费者 0 |
| 日志告警 | 只有 3 条「帧头不合法」折叠成 1 行 `WARN`（设计如此），无其它告警 |

### 这一阶留下的债

- **「一条在飞」还没做**：本阶是「拆出一帧立刻回帧」，回包在同一个分片线程里同步完成，
  所以顺序天然正确。等 C3 把业务甩给线程池，就必须靠 C2 的摘读关注来保序与背压
  （背压三件套的第 1 件还没落地）。
- **半包超时没有**：一个只发半帧的连接可以永久占着缓冲（上限 16 MiB）。属 C5。
- **帧速率没有限制**：一个客户端可以无限快地发合法帧，服务端会照单全收。属 C5/M7。
- 回显是「原样回帧」，不解析 `payload` 里的 protobuf。真正的指令分发属 C3。

## 6.4 C2 + C3 实现记录（2026-11-04，一起做）

### 为什么这两阶必须一起做

「一条在飞」的定义是「拆出一帧就摘读关注，等响应进了写缓冲再恢复」。C1 结束时响应
是在分片线程里同步组出来的，根本没有「在飞」这段时间——C2 单独做会得到一个
**永远瞬间返回的空状态机**，测不出任何东西。真正让连接停在那里等的是 C3：
把请求投给业务池，等业务线程回投。所以两阶合并。

### 落点

| 文件 | 职责 |
| --- | --- |
| `include/network/ShardMailbox.h` + `.cpp` | 业务线程 → 分片的回投通道（加锁队列 + 合并唤醒 + `detach`） |
| `include/network/CommandRegistry.h` + `.cpp` | 指令名 → 处理函数；启动期注册、之后冻结、热路径无锁查 |
| `include/business/NetworkCommandRegistrant.h` + `.cpp` | **业务只在这一处往上长**：`echo`（验收/基准用）与 `ping`（protobuf 样例） |
| `network/Shard` | 连接表改用自增 id 作 key；新增 `InFlight` 状态、`dispatchFrame`、`drainMailbox`、`resumeReading` |

一条请求的完整路径（跨线程边界标出来了）：

```
分片线程  recv → codec.push → next() 得到整帧
          → 查注册表（一次哈希）→ 状态置 InFlight、摘读关注（interest=0）
          → 投 TaskQueueLoop                          ← 跨线程边界 1
业务线程  解析 protobuf → 跑 handler → 组响应帧 → mailbox.post(id, 字节)
分片线程  drainMailbox：按 id 找连接 → 倒进写缓冲 → 立刻 send
          → 发完 → 状态回 Idle、恢复读关注
          → codec 里还压着帧？立刻接着拆（关键，见下）
```

### 六个必须写下来的判断

1. **连接标识用自增 id，不用 socket。** fd 会被内核复用，业务线程手里那个号可能在它
   回来的路上就属于另一条新连接了。自增 id 永不重复，于是不需要额外的「代次号」。
2. **mailbox 是 `shared_ptr` 独立对象，不是分片成员。** 分片可能先退出（停机、连接被断），
   而业务线程手里的任务还在跑；任务结束时往已销毁的分片成员里塞东西就是 UAF。
   `detach()` 之后 `post()` 看到关闭标记就安静丢弃。
3. **摘读关注的顺序是「先置状态、再投递」。** 反过来会出现「响应先到、状态还没置」的
   窗口：`drainMailbox` 会因为状态不是 InFlight 把这条响应丢掉。
4. **恢复读关注时必须主动消化 `codec` 里压着的帧。** 摘关注期间对端可能已经又发了
   几帧（甚至就在同一个 `recv` 块里），它们躺在 codec 的缓冲里等下一次网络事件——
   而那条连接可能再也不会有网络事件。**「同一连接连发 1000 条、最后几条永远不回」
   就是这么来的**，`--case order` 专门盯这个。
5. **写缓冲 4 MiB 上限在一条在飞下基本不可达。** 上一条响应没发完就不会派发下一条，
   写缓冲只有一个响应的量。真正的背压来自读侧：不读→没有新请求→客户端自己写不动
   （实测客户端写到 0.7~0.8 MiB 就卡住）。上限留着当「以后允许多条在飞或服务端推送」
   的最后一道闸门。
6. **指令未注册 → 断开连接。** 协议里没有错误码字段，让它活着只会诱使对端反复重试
   一条永远不可能成功的指令。

### 业务怎么接（这一阶只留框架）

```
加一条新指令 = proto 里加一个 message + NetworkCommandRegistrant 里加一处 registerCommand
```

网络层、分片数、连接管理一行都不用改。`ping` 就是照抄模板：解析请求类型 → 填响应类型
→ 序列化。handler 返回 false 时框架回一个空 payload 的同名帧并计数，**不断连接**
（一次业务数据不合法不是协议错误）。

### 实测（Windows / MSYS2 UCRT64 / 4 分片，`framed_client.py --case all`）

| 用例 | 结果 |
| --- | --- |
| 1000 条连接各发一帧 | **1000/1000** |
| 半包 / 粘包 / 5000 字节大包 | **全过** |
| **保序：单连接一次发 1000 条** | **1000/1000 顺序与内容完全一致**（验证第 4 条判断） |
| **ping：protobuf 请求 → protobuf 响应** | **通过**（业务链路打通） |
| 未知指令 | **按预期断开**，计入「未知指令 1」 |
| 非法帧三类 | **全部按预期断开** |
| 慢消费者：只发不读 | 客户端写到 **0.7 MiB 就写不动**（读侧背压生效，非服务端断开） |
| 1000 条空连接保持 | **1000/1000 在线**；分片峰值 250×4 |
| 计数器自洽 | 分片 0：拆帧 1262 / 派发 1261（差 1 = 未知指令那条，解析了但没派发）/ 回投 1261 / 丢弃 0 |
| 停机 | 退出码 0，业务任务在飞时也能干净退出（mailbox detach 兜住） |

### 这一阶留下的债

- **半包超时 / 空闲超时 / 写超时都没有**（C5）：只发半帧的连接能永久占着缓冲；
  「只发不读」的连接被背压卡住后也会一直挂着。这两类都要靠定时器回收。
- **业务线程池没有隔离**：所有指令共用 `TaskQueueLoop` 的 10 条线程，一条慢 SQL 会占住
  一个业务线程。设计文档 M10 的「业务池队列拆分」仍然待做。
- **没有分段计时**（M0/M10 的脚手架）：现在能证明「对」，但还答不了「快不快」。
- `echo` 是内置调试指令，不属于业务表；业务表里的指令要逐个在
  `NetworkCommandRegistrant.cpp` 里注册。

## 6.5 C5 实现记录（2026-11-04，定时器 + 三类超时）

### 落地位置

| 文件 | 内容 |
| --- | --- |
| `include/network/TimerQueue.h`、`src/network/TimerQueue.cpp` | 最小堆 + 活表（懒删除）+ 压紧；`TimeoutKind` 三类 |
| `include/network/Shard.h`、`src/network/Shard.cpp` | `refreshTimers` / `armRefreshingTimer` / `handleTimeouts`；计数器与退出摘要 |
| `include/network/NetworkConfig.h`、`config/networkConfig.json` | `NetworkTimeouts`：`halfFrameTimeoutMs` / `idleTimeoutMs` / `writeTimeoutMs` |
| `tools/netbench/timer_bench.cpp` | 定时器堆的量尺（M8 的 log(n) 指标） |
| `tools/netbench/timeout_client.py` | 三类超时的验收脚本 |
| `tools/netbench/timeout_fd_check.sh` | 超时后 fd 是否回落（M8 验收第二条） |

分片循环的等待时长从常量改成了 `_timers.nearestTimeoutMs(kWakeTimeoutMs)`：有定时器时精确到毫秒，
一条定时器都没有时才落到 1000 ms 的安全网上限。

### 四个值得记下来的判断

1. **取消用懒删除，不按位置删堆**。维护 `(连接标识, 超时类别) → 到期时刻` 的活表，取消只擦表（O(1)），
   堆里的条目留着，弹出时对不上活表就丢弃。堆条目数超过「活条目 × 2 + 64」时整体重建，
   长期连接不断刷新空闲超时也不会把堆撑大。
2. **校验必须比对时刻，不能只比对 key**。同一个 key 被重复挂过之后旧条目还在堆里；
   只认 key 会把「刷新前那一条」当成到期，把一条刚活跃过的连接掐掉。
3. **半包超时不顺延，空闲/写超时顺延**。半包用 `armIfAbsent`：从第一个残字节起算绝对期限，
   否则对端每秒发 1 个字节就能让连接永久占着缓冲（慢速攻击）。空闲/写用「剩余时间过半才重挂」，
   既抓「彻底不动」，又不会每次事件都压一个新堆条目。
4. **`handleTimeouts` 必须紧挨在 `removeClosedConnections` 之前**（wait 之后、清理之前）。
   第一版把它放在 wait 之前，结果每个超时都晚整整 1 秒——关闭标记要到下一轮清理才生效。
   实测 2.0 秒的超时断在 2.99 秒；挪到 wait 之后就是 2.00 秒。

### 验收（两轮，配置不同）

写超时用例与空闲超时用例**必须在不同的服务端配置下跑**：写超时要求「只发不读」，
响应一旦被内核全部吞下，服务端就回到 Idle 并挂上空闲超时；两者时长一样时先到期的永远是空闲超时，
归因就错了（第一版脚本确实把它判成「写超时通过」，而日志里写超时计数是 0）。

| 轮 | 服务端超时配置 | 用例 | 结果 |
| --- | --- | --- | --- |
| 1 | 半包 2 s / 空闲 **关** / 写 3 s | `--case half,write` | 半包 2.00 s；写 3 s 量级（Linux 只发出 2.47 MiB 就被断开） |
| 2 | 空闲 3 s | `--case idle` | 空闲 3.00 s |

日志归因（分片退出摘要）：轮 1 → `半包超时 1 / 写超时 1`；轮 2 → `空闲超时 301`（300 条 fd 检查 + 1 条脚本用例）。

### 平台差异（必须记住）

| 项 | Windows 11 / UCRT64 | Debian 12 / 6.1 内核 |
| --- | --- | --- |
| 半包超时 | 2.02 s（通过） | 2.00 s（通过） |
| 空闲超时 | 3.01 s（通过） | 3.00 s（通过） |
| 写超时 | **无法触发**：回环把 8 MiB 与 15 MiB 的响应全吞进内核缓冲，`send` 从不返回「写不动」，写定时器挂不上 | **3 s 触发**：客户端 `SO_RCVBUF=8KB` 且不读，服务端只发出 2.47 MiB 就停住 |
| fd 回落（空闲 3 s，300 条） | — | **15 → 315 → 15**，300/300 被服务端断开 |

Windows 侧「测不到」不等于「没实现」：代码路径两平台共用，Linux 已证明它工作。
但这条行为**只在 Linux 上有测试覆盖**，别在 Windows 上声称它被测过。

### 定时器堆的量尺（`timer_bench`）

| 规模 | Windows：插入 / 取消（ns/次） | Linux：插入 / 取消（ns/次） |
| --- | --- | --- |
| 1 万 | 236 / 48 | 180 / 40 |
| 10 万 | 178 / 61 | 240 / 119 |
| 100 万 | 297 / 191 | 410 / 229 |

规模差 100 倍、单次耗时只涨 1.7~2.3 倍，符合 log(n)；涨到 10 倍才说明退化成 O(n)。

### Linux 复验顺带发现的两个编译错误

`epoll` 分支写了三个月，从未在 Linux 上编译过。第一次真编，两处直接编不过：

1. `src/network/Poller.cpp` **没有 `#include <sys/epoll.h>`**——Windows 分支不需要它，
   本机编译一直是绿的，而 Linux 分支里的 `epoll_event` / `EPOLLIN` 全是未声明。
2. `src/network/Net.cpp` 两处用 `SOCKET_ERROR`（Windows 专有宏）比较 `bind` / `listen` 的返回值。
   `bind`/`listen` 在两个平台成功都返回 0，改成 `!= 0` 即可。

两处修掉之后 Linux 侧 `ninja` 干净通过，`framed_client.py` 十一项全过、1000 条空连接保持通过，
**这同时把 A6 遗留的「Linux 侧待复验」结清了**。

### 这一阶留下的债

- **没有连接速率限制**：半包超时是「单帧的绝对期限」，但对端可以「发 199 字节 → 超时前重连」无限重连。
  要挡得住得有每连接/IP 的速率限制，属 M9 之后的事。
- **空闲超时默认关闭**：要开就需要一个「什么算活跃」的业务约定（心跳指令）。协议里没有心跳，
  `ping` 是业务指令，刷新空闲计时得由客户端自己发。
- **超时精度**：有定时器时按毫秒算，实测误差 ≤10 ms；一条定时器都没有时才落到 1 秒上限。
- **关闭仍是硬关**：写缓冲里没发完的字节直接丢，在飞请求归零也没有，都属 C6。
