## 0. 为什么会有这份文档

设计文档是**目的地地图**：它写全了 11 个里程碑、每个里程碑的指标和验收。它写得全是对的（它还要负责「中途交给 AI 也能接手」这件事），但**全**恰恰是它不能当路线用的原因——一份列了 11 个里程碑的文档，没法告诉你下一行代码写什么。

具体卡住的机制有三个，都不是能力问题：

1. **每一步里同时有太多「决定」和太多「未知」**。比如 M0 第一步就要你想清楚目录怎么分、统计容器长什么样、压测客户端怎么设计——四五个决定叠在一起，就动不了了。
2. **第一阶没有任何可见反馈**。M0 是脚手架（空目录、空类、统计），做完看不见任何东西跑起来，这是最容易死在里面的一步。
3. **顺序不对**。设计文档的顺序是「一次就做对」，那需要经验；学的时候应该「先跑起来，再改造成那个形状」。

顺便说一句证据：这个项目里你已经做出来的东西——策略模式注入的线程池、图结构的任务编排 `dependOn/then`、带借条和归还语义的数据库连接池、还有那次 `getStage()` 返回引用的竞态修复——论难度都在「accept 一个 socket 然后回显」之上。所以这里不是能力问题，是**排序**问题。

## 3. 第 A1 阶：阻塞式 echo 服务器（已完成）

### 目标

一个程序：监听 `127.0.0.1:9000`，接受第一条连接，收到多少字节就原样发回去，对端关闭后干净退出。

**这一阶只处理一条连接就够了。**不要为了「以后多条连接」提前设计任何东西。

## 4. 第 A2 阶：单文件 echo 客户端（已完成）

### 目标

连 `127.0.0.1:9000`，发 N 条消息，每条都要完整收回来并逐字节比对；最后打印成功数、失败数、耗时、QPS；
只要有一条失败就以非 0 退出。

命令行：`stepA2_echo_client [条数] [消息内容] [端口] [主机] [-v]`，默认 `1000` / `hello` / `9000` / `127.0.0.1`。
消息内容写成 `#5000` 表示 5000 个 `a`，测大消息不用在命令行里敲长字符串；`-v` 逐条打印 send/recv 各调用了几次。

## 5. 第 A3 阶：每条连接一个线程的服务器（已完成 2026-09-22）

### 目标

监听 `127.0.0.1:9000`；接受一条连接就把它的回显循环交给一条独立的线程；多条连接**同时**被服务，
互不影响（A1 一次只伺候一条）。

### 必要的注意事项

1. **落地位置**：和 A1 同一个口径，直接在框架里做的——`src/network/Net.cpp` 的 `run()` 现在是
   「`accept` 之后把这条连接的 `recv`→`send` 循环打包成 `Task<std::any>` 丢进 `TaskQueueLoop`，
   然后立刻回去 `accept`」。连接 socket 归那个任务独占，任务收工时自己 `closesocket`。
2. **线程数的预设值在 `TaskQueueLoop`**（`kTaskThreadCount`，当前 10）。`ThreadPool` 的线程数已经从
   编译期常量 `THREADNUM` 改成构造参数（`_threads` 从 `array` 改成 `vector`）；要多给连接就调这个数。
3. **并发上限 = 预设值 − 1**：`net->run()` 的 accept 循环本身也是一个池任务，常驻占着 1 条线程，
   所以 10 条线程实际只留 9 条给连接。实测：挂住 8 条空闲连接时新客户端照常跑完，挂住 9 条时新客户端
   连得上但一条回显都拿不到（在排队等线程）。
4. **这 10 条线程是框架共用的**：延迟消息、连接池维护、以后的业务都在这上面排队；连接任务阻塞在
   `recv` 里占的是所有人的线程。这是 A6 要换掉它的直接原因（设计文档 M4、§2.3 铁律 6）。
5. **`send` 带 `MSG_NOSIGNAL`**（已经加了）：客户端异常断开时的 SIGPIPE 就在这条路径上。
6. 这一阶是**对照物**，B 阶段按 M4 换成分片时不带过去：分帧、背压、超时都用正确的形状在后面做，
   别在这条路上继续加功能。

（2026-09-22 实测记录：单客户端 1000 条全成功；两个客户端同时跑 300 + 300 条全成功，服务端日志里
两种消息长度交错切换 427 次——串行执行只会是 1 次；33 次「接受连接」对应 33 次「收到 0 字节，对端关闭」，
之后服务器仍能继续服务。）

## 6. 第 A6 阶：换 `epoll`，一条线程管 1000 条连接

### 这一阶的位置（为什么）

A3 的形状是「每条连接占一条池线程」：1000 条连接它**都收得下**（实测 3.1 秒全连上、全断开后 fd 回到 6、
空闲时 CPU 0.6%），但**同时只能服务 9 条**（10 条池线程减去 accept 循环自己那条）——实测 15 条连接
各发一次 `hello`，只有 9 条拿到回显。

这一阶要的形状完全不同：**一条线程 + 一个 `epoll` 集合 + 每连接一点状态**，管住全部连接。

原计划里的 A4（非阻塞 + `sleep` 忙等）和 A5（`poll` 换掉忙等）并进这一阶：不安排「故意写笨办法、
感受代价」的中间态了，但那两阶的技术点一个都不能少——顺序展开在下面「必须按这个顺序做」里。
而且它们已经有现成的参考实现：`tests/reactor_demo.cpp`（非阻塞 + `poll` + 读写缓冲 + 干净关闭，290 行，
跑 `tests/run_tests.sh reactor`）。**先读它**：这一阶是照那个形状把 `epoll` 版写进框架，不是从零推。

### 目标

一条线程（`Net::run()` 那条）管 1000 条连接：

- 1000 条连接建立后稳定保持，空闲时进程 CPU ≈ 0；
- 任何一条连接发 `hello` 都收得到 `hello`（不是只有前 9 条）；
- 客户端正常关闭、异常断开（RST）、只发一半（半包）都不影响其它连接；
- 全部关闭后 fd 数回落到基线附近（不泄漏）。

### 必须按这个顺序做（每一步都能单独跑出结果）

1. **先把非阻塞落到单条连接上**：连接 socket 设非阻塞；`recv` 的 `EAGAIN` 不当错误；`send` 部分发送
   要记游标。先让 A2 客户端 1000 条跑通——这一步的产物是「语义对了」，还不需要 `epoll`。
2. **监听 socket 也非阻塞**，`accept` 循环接到 `EAGAIN` 为止（Linux 上 `accept4(..., SOCK_NONBLOCK)`
   一次搞定）。漏了这条，第 6 步连接数一上来就会卡在 `accept` 上。
3. **连接表 + 每连接状态**：`unordered_map<int, Connection>`（`std::vector` 也行）。每条连接至少要有：
   socket、还没发完的字节、发到哪儿了（游标）、以及「这条连接是谁」的标识。
4. **接上 `epoll`（LT 模式）**：`epoll_create1` → `epoll_ctl(ADD/MOD/DEL)` → `epoll_wait`。
   到这一步你才真正拥有「一条线程管 N 条」。
5. **事件语义四件事**（这一阶的核心，写错了不是忙等就是丢连接）：
   - 常挂 `EPOLLIN`；**`EPOLLOUT` 只在「还有字节没发完」时挂，发完立刻摘**（一直挂着，`epoll_wait`
     每次都告诉你可写，等于自己造了个忙等）；
   - `epoll_wait` 返回 `-1` 且 `errno == EINTR` 要重试；
   - 可读事件里 `recv` 返回 0 就是对端关闭（`EPOLLRDHUP` 只是提示，最终以 `recv` 的返回值为准）；
   - 注册时的 `data` 里放**连接标识**，不放裸 fd（fd 会被内核复用）。
6. **压到 1000 条**：先看资源上限（`ulimit -n` 本机是 524288，够；`listen` 的 backlog 顺手调大），
   再用 `test/hold_conns.py 1000 60` 保持 1000 条，另开终端看 CPU、fd、内存。

### 这一阶真正要学的三件事

1. **poller 的事件语义与事件循环**：怎么加、怎么删、怎么等、事件回来怎么分派给「哪条连接」；
   什么时候挂 `EPOLLOUT`、什么时候摘。
2. **非阻塞读写与半包**：`EAGAIN` 不是错误；一次 `recv` 不保证是一个完整消息；`send` 会部分成功——
   「收到的字节」和「没发完的字节」是两份独立状态。
3. **连接生命周期与线程归属**：只有这条事件循环线程能碰连接；连接的删除只能放在一轮事件处理**结束之后**
   （遍历中途删就是经典的 use-after-free）。

### 这一阶不许做的事

- 不许再用 `TaskQueueLoop` / 任何额外线程来管连接（这一阶的主题就是「一条线程管 N 条」）
- 不许用 `select`（同一件事的旧写法，学不到新东西）
- 不许改量尺：`test/bin/stepA2_echo_client`、`test/hold_conns.py`
- 不许一步到位：按上面 6 步走，每步都能单独跑出结果
- 这一阶不做：分帧（C1）、业务派发（C3）、唤醒器（C4）、定时器（C5）、优雅停机（C6）

### 需要的判断依据（不给代码，只给判断标准）

- 三个调用的分工：`epoll_create1` 建集合、`epoll_ctl` 增删改、`epoll_wait` 等事件；
  `epoll_wait` 的返回值是「这次有几个事件」，可能小于你给的上限。
- **`EPOLLIN` 表示「可读」，不代表「有数据」**：可能是对端关了。可读永远要配合 `recv` 的返回值判断。
- 写缓冲：非阻塞 `send` 的返回值是实际发出去的字节数，可能是 0（发送缓冲满）。剩下的字节要留着等 `EPOLLOUT`。
- 空闲 CPU 不为 0 时，按这个顺序查：① `EPOLLOUT` 是不是常挂 ② `epoll_wait` 的超时是不是给了 0
  ③ 是不是在写缓冲为空时还在反复 `send`。
- 这一阶只做 Linux（`epoll` 是 Linux 的）。跨平台抽象是 B1 的事，别在这儿顺手封接口。

```bash
cmake --build build --parallel 4     # 然后在控制台里 network-run
```

### 怎么测

```bash
test/bin/stepA2_echo_client 1000 hello                  # 单条连接的功能回归（必须先过）
python3 test/hold_conns.py 1000 60                      # 1000 条保持 60 秒
python3 test/hold_conns.py 15 0 --echo --timeout 1      # 15 条各发一次 → 应该 15 条全成功
python3 test/hold_conns.py 1000 0 --echo --timeout 1    # 1000 条各发一次（慢一点，但最能说明问题）
```

另开一个终端看这四样：`top -H -p <pid>`（只应该有一条线程热，空闲时 ≈ 0）、
`ls /proc/<pid>/fd | wc -l`（≈ 连接数 + 少量；全关掉后回落）、`ps -o rss= -p <pid>`（内存）、
`ss -tn state established | grep :9000 | wc -l`（内核侧看到的连接数）。

**A3 的基线**（用来对照）：1000 条能连上（3.1 秒）、空闲 CPU 0.6%、断开后 fd 回到 6，
但 15 条各发一次只有 9 条成功。

### 验收（五条）

1. `stepA2_echo_client 1000 hello` 全成功、退出码 0。
2. `hold_conns.py 1000 60`：1000 条全部连上并保持住，期间没有被断开；空闲时那条线程 CPU ≈ 0
   （是「接近 0」，不是「不高」）。
3. `hold_conns.py 1000 0 --echo`：1000 条各发一次**全部成功**（A3 只能过 9 条——这就是这一阶的意义）。
4. 全部断开后 fd 回落到基线附近；客户端被突然杀掉（RST）不影响其它连接。
5. 你能说清：`EPOLLOUT` 什么时候挂、什么时候摘；「可读」为什么不能直接当成「有数据」。

### 故障对照表

| 现象 | 最可能的原因 |
| --- | --- |
| 空闲连接时 CPU 一直 100% | `EPOLLOUT` 常挂；或 `epoll_wait` 超时给了 0；或写缓冲空了还在死循环 `send` |
| 只有前几条连接有回显 | 还是 A3 的形状（池子/线程）；或 accept 只接了一个；或事件没按连接标识分派 |
| 连接一多就不接新连接了 | 监听 socket 没非阻塞、卡在 `accept` 上；或 backlog 太小 |
| 客户端断开后进程 CPU 升高 | 对端关闭那条路没把连接从 `epoll` 和连接表里删掉，之后每轮都在它身上转 |
| 偶发崩溃 / 数据错乱 | 连接对象在一轮事件遍历中途被删；或 `data` 里放的是裸 fd，fd 被复用后认成了别的连接 |
| 只收到一半回显 | 非阻塞 `send` 部分成功，剩下的没等 `EPOLLOUT` 就丢了 |
| 压到 1000 条时 `accept` 报 `EMFILE` | fd 上限（`ulimit -n`）不够，或连接关了没摘 fd |
| 1000 条里只有几百条连上 | `listen` 的 backlog 太小、或者 accept 循环没接到 `EAGAIN` |
