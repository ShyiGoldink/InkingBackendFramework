## 0. 为什么会有这份文档

设计文档是**目的地地图**：它写全了 11 个里程碑、每个里程碑的指标和验收。它写得全是对的（它还要负责「中途交给 AI 也能接手」这件事），但**全**恰恰是它不能当路线用的原因——一份列了 11 个里程碑的文档，没法告诉你下一行代码写什么。

具体卡住的机制有三个，都不是能力问题：

1. **每一步里同时有太多「决定」和太多「未知」**。比如 M0 第一步就要你想清楚目录怎么分、统计容器长什么样、压测客户端怎么设计——四五个决定叠在一起，就动不了了。
2. **第一阶没有任何可见反馈**。M0 是脚手架（空目录、空类、统计），做完看不见任何东西跑起来，这是最容易死在里面的一步。
3. **顺序不对**。设计文档的顺序是「一次就做对」，那需要经验；学的时候应该「先跑起来，再改造成那个形状」。

顺便说一句证据：这个项目里你已经做出来的东西——策略模式注入的线程池、图结构的任务编排 `dependOn/then`、带借条和归还语义的数据库连接池、还有那次 `getStage()` 返回引用的竞态修复——论难度都在「accept 一个 socket 然后回显」之上。所以这里不是能力问题，是**排序**问题。

## 3. 第 A1 阶：阻塞式 echo 服务器

### 目标

一个程序：监听 `127.0.0.1:9000`，接受第一条连接，收到多少字节就原样发回去，对端关闭后干净退出。

**这一阶只处理一条连接就够了。**不要为了「以后多条连接」提前设计任何东西。

### 文件

新建 `tools/ladder/stepA1_echo_server.cpp`，一个文件、一个 `main`。

（`tools/` 不在 `.gitignore` 里，所以它会显示为未跟踪文件；要不要提交由你决定。）

### 必须按这个顺序做

这个顺序本身就是这一阶要学的东西，每一步失败的现象都不一样，出问题时能立刻定位：

1. `WSAStartup` —— Windows 上必须先做这一步，否则后面所有 socket 调用都会失败
2. `socket` —— 创建监听 socket
3. `setsockopt(SO_REUSEADDR)` —— 让程序重启后能立刻重新绑定端口
4. `bind` —— 绑定 `127.0.0.1:9000`
5. `listen` —— 变成监听状态
6. `accept` —— 等一条连接进来（会阻塞在这里，这是预期的）
7. 循环 `recv` → `send` —— 收到多少回多少
8. 对端关闭后 `closesocket` + `WSACleanup`

### 这一阶不许做的事

提前做任何一件都会让你同时面对两个问题，然后卡住：

- 不许用非阻塞、`select`、`poll`、`epoll`
- 不许开线程
- 不许 include 框架里的任何头文件（`FrameCodec`、`ThreadPool` 都不要）
- 不许引入第三方库
- 测试先用纯 ASCII（`hello`），**不要一上来就测中文**，编码问题会把现象搞乱

### 需要的判断依据（不给代码，只给判断标准）

- `recv` 的返回值：`> 0` 是收到的字节数；`== 0` 表示对端正常关闭；`SOCKET_ERROR` 表示出错。
- `send` 的返回值是**实际发出去的字节数**，可能小于你给它的长度。所以「回显」要写成循环推进，不能只调一次就假设发完了。
- 地址结构里三个字段的含义：地址族、地址、端口；端口要用主机序转网络序。
- `SOCKET` 类型在 Windows 上**不是 int**，别用 `int` 存它。

### 编译命令（我已经在这台机器上验证过）

```powershell
& "C:\msys64\ucrt64\bin\c++.exe" -std=c++20 -O0 -g tools/ladder/stepA1_echo_server.cpp -o build/ladder/stepA1_echo_server.exe -lws2_32
```

`-lws2_32` **不能少**。我实测过：不加会报一堆 `undefined reference to __imp_WSAStartup` 之类的链接错误，加上就一次通过。

### 怎么测（不用先写客户端）

服务器跑起来之后，另开一个 PowerShell 窗口，把下面这段整体粘进去：

```powershell
$client = New-Object System.Net.Sockets.TcpClient('127.0.0.1', 9000)
$stream = $client.GetStream()
$bytes  = [Text.Encoding]::ASCII.GetBytes('hello')
$stream.Write($bytes, 0, $bytes.Length); $stream.Flush()
$buffer = New-Object byte[] 32
$count  = $stream.Read($buffer, 0, 32)
'收到: ' + [Text.Encoding]::ASCII.GetString($buffer, 0, $count)
$client.Close()
```

看到 `收到: hello` 就成了。

### 验收（四条都要过）

1. 客户端发 `hello`，收到 `hello`。
2. 同一个客户端连续发三次，三次都收到正确回显（验证循环没写错）。
3. 客户端关闭后，服务器打印收到 0 字节并自己退出，退出码 0（验证你认出了「对端关闭」）。
4. 服务器连着重启三次，每次都能立刻绑定端口不报错（验证 `SO_REUSEADDR` 的作用）。

### 故障对照表

| 现象 | 最可能的原因 |
| --- | --- |
| 编译时报 `undefined reference to __imp_WSAStartup` | 少了 `-lws2_32` |
| 链接/编译报 winsock 相关的重定义错误 | `winsock2.h` 和 `windows.h` 的头文件顺序反了（`winsock2.h` 必须在前面） |
| `WSAStartup` 返回非 0，后面全失败 | 忘了调 `WSAStartup`，或者参数写错 |
| `bind` 失败（10048） | 端口被占用（上一个服务器还在跑），或者没设 `SO_REUSEADDR` |
| 客户端连不上（10061） | 服务器没走到 `listen`，或者监听地址绑成了别的地址 |
| 客户端立刻读到 0 字节然后断开 | 服务器 `recv` 完之后立刻 `closesocket` 了，或者 `send` 用错了长度 |
| 只收到一半回显 | 忽略了 `send` 的返回值，或者 `recv` 的循环边界写错 |
| 客户端一直卡住不返回 | 服务器没走到 `send`（比如把 `recv` 的返回值当成「必须等于缓冲区大小」来处理） |
| 中文乱码 | 编码问题，这一阶不要测中文 |

1. `stepA1_echo_server.cpp` 的完整内容
2. 完整的报错文本，或者「客户端卡在哪里、屏幕显示什么」
3. 你敲的命令

贴完这三样就行，不用自己先判断是哪里错了——判断是我的活。

## 4. 第 A2 阶：单文件 echo 客户端

### 为什么

到 A1 为止，验证都是靠别人的脚本（PowerShell 片段）做的。后面每一阶都要验证，你需要自己的客户端，
而且客户端要面对的坑（connect、部分收、部分发）和服务端不是同一批。它同时是设计文档里 `tools/netbench` 的种子。

### 文件

`tools/ladder/stepA2_echo_client.cpp`，单文件、独立编译，**不属于框架**，不 include 框架任何头文件。

### 目标

连 `127.0.0.1:9000`，发 N 条消息，每条都要完整收回来并逐字节比对；最后打印成功数、失败数、耗时、QPS；
只要有一条失败就以非 0 退出。

命令行：`stepA2_echo_client.exe [条数] [消息内容] [端口]`，默认 `1000` / `hello` / `9000`。

### 必须按这个顺序做

1. `WSAStartup`
2. `socket`
3. `connect` 到目标地址
4. 循环 N 次：把整条消息发完 → 把同样长度的回显收满 → 逐字节比对
5. `closesocket` + `WSACleanup`

### 这一阶真正要学的三件事

1. **发要循环**：`send` 的返回值是实际发出去的字节数，一次可能发不完。你服务端已经写对了，客户端同理。
2. **收也要循环**：`recv` 一次不保证拿到你要的全部长度，要「收满"这条消息的长度"」才算一条完成。
   `recv` 返回 0 是对端关闭，小于 0 是出错。
3. **这是纯字节流，没有消息边界**：等你发大消息、或者连着快发的时候，会亲眼看到「一条消息」在网络里
   被切成好几段、或者几条粘在一起。现在能靠「发一条读一条、长度已知」勉强对上——这正是以后要用
   帧格式解决的事（C1）。这一阶你要把这个现象看到。

### 编译

```powershell
& "C:\msys64\ucrt64\bin\c++.exe" -std=c++20 -O0 -g tools/ladder/stepA2_echo_client.cpp -o build/ladder/stepA2_echo_client.exe -lws2_32
```

### 验收

1. 默认参数跑 1000 条，全部成功，退出码 0。
2. 服务端日志里对应出现 1000 次「收到 5 字节」和 1 次「收到 0 字节，对端关闭」。
3. 发一条大消息（一条 5000 字符的消息）：客户端能完整收回并比对通过；**服务端会打印多次「收到 N 字节」**，
   因为服务端收缓冲区是 4096。这是 A2 最重要的观察点。
4. 服务端没开时运行客户端，给出一行清楚的错误（不是崩溃），退出码非 0。

### 顺带记一笔

服务端现在每收到一条消息就往控制台打一行。1000 条就是 1000 行，这会成为 A2 测出来的 QPS 的主要瓶颈。
这是故意的——先让你看见「每条都打屏」有多贵。等接上设计文档 M0 的分段计时，这里要换成只累加计数、
每秒汇报一次。

### 卡住时贴什么给我

源码 + 完整报错/现象 + 你敲的命令，三样。
